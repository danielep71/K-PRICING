# 🧮 Excel oracle

The Excel oracle computes the worksheet-function cases of the date layer a
second time, with Excel's own worksheet functions, and compares each result
with the case's expected file. Microsoft wrote those functions; the date
layer's code and the reference model of `tests/derivations/` never compute an
oracle result. An error that the derivation of the expected values and the
date layer's code could share therefore shows up as a disagreement, wherever
Excel's functions and the [calculation contracts](CALCULATION_CONTRACTS.md)
agree.

## How it runs

`tests/modules/TEST_ExcelOracle.bas`, the project suite `excel-oracle`, is
generated by `tools/gen_excel_oracle_suite.py` from `tests/fixtures/` and
`tests/expected/`. For each covered case it evaluates one formula with
`Worksheet.Evaluate` on a scratch workbook in the 1900 date system, encodes the
value as the [expected files](TEST_CASES.md#worksheet-function-cases) do, and
asserts that it equals the expected text. The suite is in the evidence policy,
so the [Excel run](../repo_governance/EXCEL_RUN.md) certifies it: its passed
assertions are the oracle's agreement count. `tests/test_excel_oracle_suite.py`
fails while the module is stale, when a formula calls a function outside the
list below, and when the module names a procedure of the date layer.

```sh
python tools/gen_excel_oracle_suite.py --write   # regenerate the module
python tools/gen_excel_oracle_suite.py --list    # every covered and excluded case
```

`--list` prints each covered case with its formula and expected text, and
each excluded case with its reason.

## Allowed functions

A formula calls only `DATE`, `YEAR`, `MONTH`, `DAY`, `EOMONTH`, `EDATE`, `WEEKDAY`, `INT`, `MOD`, `IF`, with arithmetic and
comparison operators. Every argument is a literal: a date as `DATE(y,m,d)`, a
serial or a whole number as itself, a Boolean as `TRUE` or `FALSE`.

| Function | Identity | Notes |
| --- | --- | --- |
| `KPR_Dates_DayOfWeek` | `WEEKDAY(d,2)`, or `WEEKDAY(d,1)` when `Opt_WeekBaseMonday` is `FALSE` | |
| `KPR_Dates_DaysInMonth` | `DAY(EOMONTH(d,0))` | |
| `KPR_Dates_DaysInYear` | `DATE(y,12,31)-DATE(y,1,1)+1` | Not for 1900 |
| `KPR_Dates_IsLeapYear` | `DAY(EOMONTH(DATE(y,2,1),0))=29` | Not for 1900 |
| `KPR_Dates_BeginOfMonth` | `DATE(YEAR(d),MONTH(d),1)` | |
| `KPR_Dates_EndOfMonth` | `EOMONTH(d,0)` | |
| `KPR_Dates_BeginOfQuarter` | `DATE(YEAR(d),INT((MONTH(d)-1)/3)*3+1,1)` | |
| `KPR_Dates_EndOfQuarter` | `EOMONTH(DATE(YEAR(d),INT((MONTH(d)-1)/3)*3+3,1),0)` | |
| `KPR_Dates_BeginOfYear` | `DATE(YEAR(d),1,1)` | |
| `KPR_Dates_EndOfYear` | `DATE(YEAR(d),12,31)` | |
| `KPR_Dates_IsMonthEnd`, `IsQuarterEnd`, `IsYearEnd` | `d` equals the period end above | |
| `KPR_Dates_AddDays`, `AddWeeks` | `d+n`, `d+7*n` | |
| `KPR_Dates_AddMonths`, `AddYears` | `EDATE(d,n)`, `EDATE(d,12*n)`; with `Opt_KeepEOM` `TRUE`, `EOMONTH(d,n)` when `d` is a month end | |
| `KPR_Dates_NthWeekdayOfMonth` | `DATE(y,m,1)+MOD(w-WEEKDAY(DATE(y,m,1),b),7)+7*(n-1)` | `b` is 2, or 1 for a Sunday base |
| `KPR_Dates_LastWeekdayOfMonth` | `EOMONTH(DATE(y,m,1),0)-MOD(WEEKDAY(EOMONTH(DATE(y,m,1),0),b)-w,7)` | As above |

`KPR_Dates_PillarFromDates`, `KPR_Dates_DateFromPillar` and
`KPR_Dates_HostDateSystem` have no Excel worksheet function: the pillar
grammar and the host diagnostic are the date layer's own contracts.

## Exclusions

A case is covered only where Excel's functions and the contracts agree. A
case is excluded, with its reason, when:

- its caller is a 1904 workbook: the refusal under 1904 is the date layer's
  rule, not Excel's;
- its function has no Excel worksheet function;
- it expects an error: Excel has none of the date layer's conditions;
- an argument is text, which Excel converts by the regional settings, while
  the date layer accepts only `YYYY-MM-DD`;
- an argument is an array: the oracle evaluates one value per case;
- an argument is a fractional number or a date with a time, which the date
  layer reads by its own rounding rules;
- an argument is of another type, such as Empty or an error value, which
  Excel converts differently;
- it asks `KPR_Dates_IsLeapYear` or `KPR_Dates_DaysInYear` about 1900, which
  Excel counts as a leap year ([SRC-04](SOURCES.md)).

## What it proves

A passing `excel-oracle` run shows that Excel's functions give each covered
case's expected value. It does not change a value's
[reference class](TEST_CASES.md#reference-classes): the expected values stay
`illustrative`, and the holdouts of the draft accuracy contracts stay sealed.
It says nothing about an excluded case, and both computations read a date as
a serial of the 1900 date system, so an error in that reading is outside its
reach.
